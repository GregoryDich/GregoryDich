## 1. Purpose
Estimate the inter-coder reliability of the AI × jobs narrative coding scheme (`CODEBOOK.md` v1: relevance 0/1; valence minus / plus / mixed / none) and apply the pre-registered go/no-go gate for WS1: **Cohen's κ ≥ 0.70** for relevance and for valence.

## 2. Materials
300 fragments (~50 words each) drawn from 14 YouTube auto-transcripts on AI and work (video IDs deposited with the data), stratified as 136 dictionary-relevant / 164 dictionary-non-relevant with seed 42 (`ws1_pipeline.py`). This is a **reliability sample**, chosen to contain both classes; it is not an estimate of the corpus. Corpus-level validation (≥1,000 fragments, crowd coders) is WS1 step 1c.

## 3. Instrument
Web page (`make_artifact_page.py`): one fragment at a time; per-coder random order seeded by the coder's pseudonym; relevance first, valence only if relevant; no back navigation; 8 constructed practice items with immediate feedback before the 300; instructions in English, Russian and Hebrew — **fragments always in English**. The page records per fragment: label, position in the coder's order, seconds spent; per session: pseudonym, self-reported English level, recruitment source (public post / researcher personally / other), interface language, start and end timestamps, codebook version. Results are exported by the coder as CSV.

## 4. Coders and recruitment
The PI, personal acquaintances of the PI, and volunteers recruited through an anonymous public post (`RECRUITMENT.md`). The recruitment text describes the task only as coding "how videos talk about AI and work"; no hypothesis is mentioned. Coders are asked to work alone and not to discuss fragments. Coders give consent on the page to publication of their pseudonymised coding. No personal data beyond a self-chosen pseudonym is collected.

## 5. Inclusion rules (fixed in advance)
A coder's data enter the primary analysis if all hold: (a) self-reported English level *good*, *fluent* or *native*; (b) practice score ≥ 6 of 8 on the first attempt; (c) all 300 fragments completed; (d) median time per fragment ≥ 3 seconds. Excluded coders are reported with the reason; their data are kept for secondary analysis.

## 6. Primary analysis
Cohen's κ, computed separately for relevance (2 categories, all 300 fragments) and valence (4 categories, on fragments both coders marked relevant; a second version on all 300 with *none* for non-relevant is reported as well), with 95% bootstrap confidence intervals (1,000 resamples over fragments).
**Primary pair(s):** if two or more *publicly recruited* coders are eligible, all pairs among them; otherwise all pairs among eligible non-PI coders. **The PI's coding is never part of the primary κ.** Gate: mean pairwise κ ≥ 0.70 on both dimensions.

## 7. Secondary analyses
Krippendorff's α across all eligible coders (also using partial completions); κ of the PI versus each other coder; κ by recruitment source and by interface language; agreement of the machine channels (dictionary v0/v1, LLM) with adjudicated gold labels; timing distributions.

## 8. Adjudication
Gold label per fragment = majority among eligible coders; ties are broken by the PI's label, and the number of PI tie-breaks is reported.

## 9. Decision rule
Gate passed → WS1 starts with the codebook unchanged. Gate failed → codebook v2 written from the disagreement patterns, deposited on OSF, and the reliability study repeated with new or re-trained coders; if valence alone fails twice, the fallback is a binary alarming/reassuring scheme, declared as a deviation.

## 10. Data deposit
Raw per-coder CSVs (pseudonymised), the κ report, this protocol, `CODEBOOK.md` v1 and the recruitment text are deposited on OSF when the analysis is complete.

## 11. Disclosure
`CODEBOOK.md` v1 was written on 2026-06-20, after the OSF registration (2026-06-19) and after a pre-test in which two large language models coded the same 300 fragments (κ 0.48 for relevance, 0.22 for valence). That pre-test motivated rules 1–2 of the codebook (debunking = plus; doubt about the cause = none). The LLM codings are not human data and are not used in any reliability estimate.

**12.1 Corrections to version 1**
- (a) *Section 2, stratification.* The 300 fragments were drawn by dictionary **v1** (12.5.1), so the stratification by the drawing dictionary is **140 dictionary-relevant / 160 dictionary-non-relevant**, not 136 / 164; 136 is the number that dictionary v0 (12.5.2) marks relevant among the same 300, and every v0-relevant fragment among them is also v1-relevant. Evidence: the 300 contain 140 v1-relevant fragments, which is every v1-relevant fragment of the 431-fragment corpus (`ws1_summary.md` as written by the v1 pipeline run committed in `7eb5a1e`). `ws1_pipeline.py` puts every relevant fragment into the sample (up to 70% of it), so this is certain under a v1 draw; under a v0 draw the 4 fragments that only v1 marks relevant would all have had to fall among the 164 fragments drawn from v0's 295 non-relevant ones, probability C(291,160)/C(295,164) = 0.094, a likelihood ratio of about 10.6 in favour of v1. The pipeline writes `fragments.csv` and `coding_sample.csv` in one run, and that v1 run (`7eb5a1e`, 2026-06-20 00:28 UTC) precedes the first commit of `ws1_survey.html`, which holds the 300 (`2453bb2`, 12:30 UTC). The original `fragments.csv` and `coding_sample.csv`, like the transcripts, are git-ignored and not in the repository, so the draw cannot be repeated from the repository.
- (b) *Section 8, gold labels (clarification).* The PI does not vote. The majority label of a group of coders is the label given by more of them than any other label; when two or more labels share the highest count, that is a tie. **Relevance:** the gold label is the majority label among the eligible (section 5) coders other than the PI; a tie is broken by the PI's label for that fragment and counted as a PI tie-break; if the PI did not code, or did not code that fragment, the fragment's gold relevance is unresolved. **Valence:** if gold relevance is 1, gold valence is the majority valence among the eligible non-PI coders who marked the fragment relevant; a tie is broken by the PI's valence only if the PI marked the fragment relevant, and is otherwise unresolved. If gold relevance is 0, gold valence is `none`. A fragment whose gold label on a dimension is unresolved is left out of the comparisons with gold labels on that dimension; the number of such fragments is reported together with the number of PI tie-breaks. The other reading of section 8, in which the PI votes as one of the eligible coders (when the PI meets section 5) and ties are again broken by the PI's label, is reported as a sensitivity analysis.
- (c) *Sections 6 and 9, the gate decision (clarification).* A pairwise κ is undefined when the pair has no fragment to compare on that dimension (for valence: no fragment that both coders marked relevant) or when chance agreement is 1 (both coders gave one and the same label to every compared fragment); a mean pairwise κ is undefined when any of its pairwise κs is. The gate requires a mean pairwise κ ≥ 0.70 on both dimensions (section 6), so a mean below 0.70 on either dimension is a failed gate (section 9), whether the other dimension's mean is at least 0.70, below it or undefined; the report states why a mean is undefined. Valence fails *alone* (the fallback of section 9) only when the relevance mean is at least 0.70. The gate cannot be evaluated only when there is no primary pair, or when no mean is below 0.70 and at least one is undefined; section 9 then takes no decision, the report states the cause, and any decision the researchers take in that case is reported as a deviation from this protocol.

**12.2 Scope relative to the registration**
- (a) *X− and X+ (A.2).* The registration builds the destruction index X− from fragments "classified for AI-occupation co-occurrence using both a keyword dictionary and an LLM classifier", and the creation index X+ from "the same pipeline applied to a second lexical channel: 'AI side hustle,' 'vibe coding,' 'AI democratizes,' and related phrases". The codebook's relevance variable is the AI × occupation classification. Its valence variable codes the stance of AI × occupation fragments (minus = alarming; plus = reassuring, which covers both creation and the debunking of destruction; mixed; none). The valence code is not the X+ lexical channel: *plus* includes debunking, which the X+ phrases do not name, and the 300 fragments were not retrieved through the X+ phrases (none of them contains "side hustle", "vibe cod…" or "democratiz…"). Agreement on valence therefore validates stance coding within the AI × occupation stream; it does not validate retrieval through the X+ lexical channel, which this study does not test.
- (b) *Dictionary-only vs. LLM-only index (A.6, item 3).* Dictionary v1 is v0 as revised in `7eb5a1e` (the stance override: a new `SKEPTICAL_TERMS` list, partly moved from `CREATE_TERMS`, that counts toward relevance and forces valence plus). That revision was made after the dictionary had been compared with 50 labels that the AI co-author, a Claude model, produced in a chat session on 2026-06-20 (ROADMAP D29), and it was tuned on those 50 fragments. The LLM channel is also a Claude model, and both `CODEBOOK.md` v1 and the LLM prompt were drafted by the AI co-author. Agreement between the dictionary-only and the LLM-only index is therefore not fully independent evidence of robustness to the classification method; it is reported as registered, with this caveat. Each channel is validated against the human gold labels (section 7, 12.1(b)), and that validation, not the agreement of the two channels with each other, is the evidence for either channel.

**12.5.3 LLM channel v1.** `ws1_llm_channel.py`: one request to the Anthropic Messages API per fragment; fragments are never combined in one prompt.
- Model `claude-opus-5-5` (Claude Opus 5.5), the current Opus model and the default in Anthropic's Claude API reference (the `claude-api` reference bundled with Claude Code; model list as of 2026-10-06). The reference gives no dated snapshot identifier for this model; dated identifiers exist only for older models. A current model was preferred to an older dated snapshot because this channel, once validated, has to be applied to the full WS1 corpus, and older models are retired first (the reference lists several 2024–2025 models as retired or deprecated). The model that served each response is logged and written next to each label, so a change of the served model would be visible.
- Request: system prompt = the complete file `llm_channel_prompt_v1.txt`; one user message, `Code this fragment.\n\n<fragment>\n{fragment}\n</fragment>` with the fragment text; `thinking: {"type": "adaptive"}`; `output_config.effort: "low"`; `max_tokens: 4096`; structured output (`output_config.format`, JSON schema: `relevant` integer in {0, 1}, `valence` in {minus, plus, mixed, none}, no other properties); the system prompt is marked for prompt caching (a cost and latency setting). No tools, no sampling parameters, no fallback model.
- Prompt and instruction parity: the prompt gives the model the information the human coders have, with the exception stated below. It contains the `CODEBOOK.md` v1 rules (the strict two-token relevance rule — an AI referent AND a labor referent AND a connection, judged from the fragment's own words only — the four valence categories, rule 1: debunking destruction = plus, rule 2: doubt about the cause = none, the decision flow and the output format), followed, as worked examples, by the 8 practice items of the page builder (practice set `3fa31542cb4a`), each with its codebook answer and its English explanation verbatim, in the form the page shows after each practice item ("Codebook answer: relevant = Yes, valence = Alarming (minus). …"), and with the same answer in the output format. A coding page built with this set shows the same practice items, answers and explanations, in the coder's interface language, and the rules in condensed form; the condensed form leaves out five of the rule-text examples that paraphrase claims of evaluation fragments, which the prompt carries (12.4.1). Parity therefore holds for the rules and the practice items, not for those five examples, and only for the coders whose page carried this set, which the `practice_set` column of each coder's export shows. No evaluation fragment is quoted in the prompt: the decision-example tables of `CODEBOOK.md` are left out because they quote evaluation fragments (12.4.1), and `tests/test_llm_channel.py` checks that the prompt shares no five-word sequence with any of the 300 fragments or with those tables and contains no frag_id. The rule text in the prompt does paraphrase, with their codes, the claims of the seven anchor fragments named in 12.4.1. Each request carries exactly one evaluation fragment, in the user message. `verify_frozen_channels.py` checks that the worked examples are, verbatim, the practice items the page shows, so a later change of the practice items would show as a broken parity.

The runner does not itself compare that table with this section, so a runner changed together with the table would still run; what makes such a run inadmissible is 12.6.2. `verify_frozen_channels.py` checks that every value of its table is written in this section, and that every run record of this channel in the code folder carries the four values; `ws1_reliability.py` compares the four values in the run record of the labels it reads with the values written here and warns when any differs.
- Determinism: this model rejects `temperature`, `top_p` and `top_k`, and its reasoning cannot be switched off; Anthropic's reference notes that temperature 0 never guaranteed identical outputs on earlier models either and, where determinism was the intent, points to effort `low` with a tighter prompt; effort `low` is the setting used. Outputs are therefore not guaranteed to be identical from run to run; the run of record is defined in 12.6.
- Pre-specified handling: HTTP 408, 409, 429 or ≥ 500 and connection errors are retried with exponential backoff (or after the server's `retry-after`), every attempt logged; any other API error stops the run, which resumes on the next start without repeating finished fragments. A refusal (`stop_reason: "refusal"`) is recorded, not retried and not sent to another model; the label stays missing. A reply that is not a valid label (cut off at `max_tokens`, or not matching the schema) leads to the identical request being repeated, at most 3 attempts in all, after which it is recorded as invalid and the label stays missing. `relevant = 0` with a valence other than `none` is recorded with valence `none` (codebook: "If relevance = 0, write none"), and the number of such cases is reported. Missing LLM labels are not imputed.

The raw log `llm_raw_log.jsonl` (every attempt: the request with the system text replaced by its hash; the response as returned, with served model, request id and token usage; timestamps) contains fragment text and is git-ignored; the SHA-256 in the run record identifies it. The runner never overwrites the run record of another run.

**12.6 Run of record and commitments**
1. Neither channel is modified until the WS1.0 gate (section 6) has been computed. Any revision of either channel made after human labels have been seen is a new version (dictionary v2, LLM channel v2). It is evaluated only on fresh fragments that are not among these 300; results of a revised channel on these 300 fragments are reported, if at all, as in-sample.
2. A run of the LLM channel is one raw log, identified by the run id in its records. It may take several invocations (an interrupted run resumes without repeating finished fragments) and is complete when every fragment has a final record: a label, a refusal or an invalid reply. A run is a run of LLM channel v1 only if its run record carries the four identities (i)–(iv) exactly as written in 12.5.3 of this version, whatever the `FROZEN` table of `verify_frozen_channels.py` holds at the time; before each invocation of the runner, `verify_frozen_channels.py` is run, and the runner is started only if it exits 0. The **run of record** is the first complete run of LLM channel v1 whose `llm_labels.csv` and run record are committed and pushed to the project repository before the first coder CSV is opened, at a commit at which `verify_frozen_channels.py` exits 0; that commit identifies it. Every other complete run of LLM channel v1 is a replicate and is reported as one, with its agreement with the run of record. A run whose run record carries other identities is output of another channel version: it is neither the run of record nor a replicate, and its labels are not reported as output of LLM channel v1.
3. If no complete run has been committed by the time the first coder CSV is opened, the run of record is the first complete run of LLM channel v1 (12.6.2) committed after that, under the same conditions, and the report states that it was made after the human labels had been opened.
4. The 50 fragment labels produced on 2026-06-20 by the AI co-author inside a chat session (ROADMAP D29) are not output of this channel: they did not come from a reproducible call with a fixed model, prompt and parameters. They are excluded from every analysis under this protocol, as are the pre-test codings disclosed in section 11.
