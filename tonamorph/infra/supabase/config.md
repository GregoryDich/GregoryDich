# Supabase project configuration

Everything below is dashboard/CLI configuration that is not expressible in
`db/migrations/`. Apply it once per project (production and staging).

## 1. Storage: private bucket `jobs`

Storage → New bucket:

| setting | value |
|---------|-------|
| name | `jobs` |
| public | **off** (private; clients only ever receive signed URLs) |
| file size limit | 64 MB (four 60 s stereo WAV stems ≈ 42 MB plus MIDI and JSON) |
| allowed MIME types | `audio/wav`, `audio/x-wav`, `audio/midi`, `audio/x-midi`, `application/json` |

Objects are written by the backend as `<user_id>/<job_id>/<file>` (contract §2:
bucket `jobs/<user_id>/<job_id>/`). Do **not** add RLS policies on
`storage.objects` for the `anon` or `authenticated` roles: only the service-role key
(backend) touches the bucket, and users get 24 h signed URLs generated by the API.

Supabase Storage has no lifecycle rules. Expired objects are deleted by the backend
cleanup (Storage API); `cleanup.sql` only removes the database rows. On AWS the S3
lifecycle rule in `infra/aws/modules/storage` does the equivalent.

## 2. Auth (GoTrue)

Authentication → Providers → Email: enabled, **Confirm email** on, minimum password
length 8. Magic links are used by the website only; the plugin signs in with
email + password through `POST /v1/auth/token` (contract §1).

Authentication → Settings:

| setting | value | why |
|---------|-------|-----|
| JWT expiry | 3600 s | matches `expires_in` in the token response |
| Refresh token rotation | enabled, reuse interval 10 s | the plugin refreshes via `POST /v1/auth/refresh` |
| Site URL / redirect URLs | the website origin(s) | magic-link redirects |
| Rate limits (token) | keep defaults | the API has its own 10 jobs/min limit |

New accounts receive 3 credits via the database trigger shipped in
`db/migrations/` (contract §3); no Auth hook is needed.

## 3. JWT verification settings for the backend

The API verifies `Authorization: Bearer <access_token>` locally (contract §1):

| backend variable | where to find it |
|------------------|------------------|
| `SUPABASE_URL` | Project Settings → API → Project URL |
| `SUPABASE_JWT_SECRET` | Project Settings → API → JWT Settings → JWT Secret (HS256 projects) |
| `SUPABASE_JWKS_URL` | `https://<ref>.supabase.co/auth/v1/.well-known/jwks.json` (projects using asymmetric ES256/RS256 signing keys; leave `SUPABASE_JWT_SECRET` empty) |
| `SUPABASE_SERVICE_ROLE_KEY` | Project Settings → API → service_role key; **backend only**, never in the plugin or `growth/` |

Required claims checked by the backend: `sub`, `exp`, `aud == "authenticated"`.

On AWS these values live in Secrets Manager (`<project>-<env>/SUPABASE_JWT_SECRET`,
`<project>-<env>/SUPABASE_SERVICE_ROLE_KEY`); `SUPABASE_URL` is a plain task
environment variable set from the Terraform variable `supabase_url`.

## 4. Extensions and scheduled cleanup

Database → Extensions: enable `pg_cron`. Then run `cleanup.sql` in the SQL editor
(or `supabase db execute -f infra/supabase/cleanup.sql`) **after** the migrations
in `db/migrations/` have been applied — it references `expire_credits()` and
`reap_stale_jobs(int)` from there. The file is idempotent.

## 5. Checklist

1. Bucket `jobs` exists, private, no anon/authenticated storage policies.
2. Email auth enabled with confirmation; JWT expiry 3600 s; refresh rotation on.
3. Backend secrets populated (`SUPABASE_JWT_SECRET` or `SUPABASE_JWKS_URL`,
   `SUPABASE_SERVICE_ROLE_KEY`).
4. `pg_cron` enabled and `cleanup.sql` applied; `select * from cron.job;` lists
   the three `tonamorph_*` jobs.
